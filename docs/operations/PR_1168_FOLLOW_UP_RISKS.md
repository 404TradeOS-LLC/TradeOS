# Athena chat transaction split: follow-up risks from PR #1168

[PR #1168](https://github.com/404TradeOS-LLC/TradeOS/pull/1168) merged at `a498084986c66f8fbb36fa3550d4747551b914d7`. Chat now opens short row level security (RLS) sessions from the authenticated actor and waits on the model without a request transaction. The merge contains no schema or policy changes. The [review fixes](https://github.com/404TradeOS-LLC/TradeOS/pull/1168#issuecomment-7232033279) keep explicitly injected audit transactions on their original connection and roll back failed, expired, or cancelled tool mutations together with their idempotency records. The following risks remain.

| Follow-up risk | Evidence and impact | What would close it |
| --- | --- | --- |
| **Authorized resource lookups can fail closed.** | The [kernel](../../app/modules/athena-kernel/service.ts#L402) calls `evaluateAthenaPermission` before entering the action's RLS transaction. The [policy](../../app/modules/athena-permissions/policy.ts#L63) can call tenant scoped database services for customers, estimates, costbook items, or technician job assignments. An actor in async context alone does not set the database session variables. The [outside-diff review finding](https://github.com/404TradeOS-LLC/TradeOS/pull/1168#pullrequestreview-6094855672) therefore still applies: an allowed object can appear missing and produce `athena_permission_object_scope_denied` (403). The source shows a denial path, with no evidence of cross-tenant disclosure. | Run the database backed permission check in a short actor scoped session. With the restricted PostgreSQL role, exercise an enabled resource scoped tool such as customer summary on an allowed object and verify that foreign objects and out-of-scope assignments are still denied. |
| **Partial records can hide provider spend or leave misleading execution state.** | [Generation and execution writes](../../app/modules/athena-kernel/executionStore.ts) commit separately. A successful provider call followed by a failed generation insert leaves no row for the [daily spend calculation](../../app/prisma/migrations/20261127050000_add_athena_org_daily_spend/migration.sql#L49). A later failure can leave an old nonterminal execution or a generation linked to an execution that never completed. The original middleware rolled back failed requests as a unit; [the split deliberately preserves earlier writes](../CURRENT_STATE.md). | Define which records operators should reconcile and which to retain as valid failure evidence. Verify detection with forced failures after provider completion and before finalization. Compare recorded spend with known provider usage for the missing-generation case and agree on a way to account for or bound the gap before PR-5 write coalescing; keep Billy's audit agreement as the PR-5 gate. |
| **A failed or lost response can follow a committed action.** | The [action commits](../../app/modules/athena-kernel/service.ts#L499) before finalization and [HTTP response delivery](../../app/backend/controllers/athena.controller.ts#L125). Same-key replay applies only for eligible actions with a matching tool, version, and input; the [engine](../../app/modules/athena-action-engine/engine.ts#L375) skips deduplication for tools that declare it unsupported. A client that assumes an error implies rollback could repeat a mutation. The rollback fix covers failures inside the action transaction. | Exercise failure or disconnect after a successful commit, then retry with the same key. Verify one mutation and replay for a deduplication eligible action. Check what the UI offers for a mutating tool without replay protection and document which outcomes callers can safely retry. |
| **Staging still needs proof of pool release and tenant isolation.** | The [route test](../../app/tests/athena-chat-route-split.test.ts) builds its own middleware chain, the unit test counts mock transactions, and the [live test](../../app/tests/athena-chat-tx-split.integration.ts#L119) observes a committed row during provider wait. That row does not rule out a second open transaction. The supplied record contains no staging run against the merged candidate. | The PR queue runner should record the deployed SHA and authenticated results for two tenants through the real route. Verify active-member success, inactive or suspended membership denial, and no cross-tenant data or identity carryover on reused connections. During a controlled provider wait, observe transaction state or verify that an independent operation can borrow the sole application pool connection before the provider resolves. Keep PR-6 server Data Cache gated on the two-tenant staging proof. |
| **Timeout and merge status documentation can mislead operators.** | The [API reference](../API_REFERENCE.md) groups provider and request timeouts under HTTP 504, while the [controller](../../app/backend/controllers/athena.controller.ts#L44) maps provider cancellation to 499 and request expiry to 504. [Architecture](../ARCHITECTURE.md#athena-production-readiness-boundary) describes a request scoped RLS session as universal in its Athena section, and [Current State](../CURRENT_STATE.md) still says PR pending. | Confirm the nonretryable `athena_provider_timeout` (499) and `athena_deadline_exceeded` (504) responses through the HTTP route and the web client's retry behavior. Align the docs with the verified status codes and short sessions, and distinguish merged status from staging acceptance. |
