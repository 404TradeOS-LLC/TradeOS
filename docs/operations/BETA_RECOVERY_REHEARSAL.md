# Disposable beta recovery rehearsal

Run `node scripts/beta-recovery-rehearsal.mjs --output=<private-local-directory>` from the repository root with local Docker available. No database URL, existing container, cloud credential or remote object endpoint is accepted. The runner creates a uniquely named disposable PostgreSQL 16 container and either a RustFS 1.0.5 container or a local RustFS process. It removes only its own containers, volumes and temporary storage afterward. PostgreSQL has no published port; the S3 port is bound to loopback. Synthetic backup bytes and the JSON receipt remain in the selected directory with private permissions. Retain that directory privately; do not commit binary backups.

The runner creates a tiny synthetic organization/document schema with a foreign key and forced tenant RLS, and uploads a private synthetic object. It takes a custom-format `pg_dump` and exports the object bytes, writes one database row after the snapshot, drops the source database, deletes the source object, and proves both sources absent. It restores the dump into a separate database and uploads the retained object into a separate private bucket. Verification checks exact row equality, exclusion of the later write, FK enforcement, enabled/forced RLS, own-tenant visibility and foreign/unscoped denial under a newly provisioned non-superuser/non-bypass role, matching object SHA-256, and anonymous object denial. Roles/grants are explicitly provisioned because cluster-global roles are outside a database dump.

The receipt records backup duration, restore-and-verification duration, incident-to-verified-recovery duration and the measured interval between snapshot and simulated incident. These are observations for this tiny synthetic fixture, not a service RTO/RPO commitment. The database and object exports are sequential rather than an application-consistent multi-resource snapshot. The deliberately excluded post-snapshot row demonstrates that snapshot recovery loses later writes.

## Limits and release gate

This is an actual local PostgreSQL and S3-compatible object restore. It does not execute TradeOS migrations or prove recovery of the application schema, Supabase Auth/Storage metadata and policies, provider-managed backups/PITR, production permissions, encryption/retention, recovery at realistic data volume, or a protected staging/production restore. RustFS is an independent local S3 implementation, not the deployed Supabase Storage adapter. Its anonymous denial proves the rehearsed bucket is private, not the application's organization-scoped storage authorization. Production backup/PITR certification and the complete invited-beta Recovery and operations gate remain open. The release operator must retain a provider/application-specific rehearsal and founder-approved recovery expectations, rollback target, alerts and support owner before GO.

Registry dependency recovery: Docker Hub/Quay MinIO pulls were denied and the historical MinIO binary endpoint returned HTTP 410 in this environment; the runner uses RustFS 1.0.5 instead. No paid infrastructure or production data is needed.

## Low-disk runtime fallback

`--rustfs-binary=<absolute-local-path>` starts an already installed RustFS binary with a fresh temporary data directory, generated credentials, a loopback S3 address and console disabled. The receipt records its binary hash. Install the Linux x86_64 musl 1.0.5 release from `https://github.com/rustfs/rustfs/releases/tag/1.0.5` and verify the archive against the release's `SHA256SUMS` before extracting. The verified archive hash for `rustfs-linux-x86_64-musl-v1.0.5.zip` is `3d9d42bb4cb7a1589266090d4f9f8238465506cdd9d5e897193377dd6f610aac`. This avoids Docker's larger multi-layer S3 image on vfs storage. The binary is a trusted local executable; no download or arbitrary endpoint is executed by the runner. PostgreSQL still requires Docker.
