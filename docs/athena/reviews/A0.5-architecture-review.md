# Athena A0.5 Architecture Review

Status: Draft review for PR
Milestone: A0.5 - Architecture Review
Date: 2026-08-09
Scope: Documentation and architecture validation only

## Executive Verdict

READY FOR A1 WITH REQUIRED CORRECTIONS

The Athena Platform Bible is directionally sound and does not require a foundational redesign before implementation. Its strongest decisions are the explicit boundary that Athena must execute through tools and application services, permission enforcement outside the LLM, invisible orchestration, and the commitment to stable contracts.

A1 should not begin as a broad assistant implementation. A1 is approved only as a narrow kernel foundation after the required corrections below are accepted into the A1 implementation plan or the Bible contracts. The highest-risk gaps are not conceptual contradictions; they are missing executable detail around lifecycle state, cancellation, context minimization, freshness evidence, and object-level authorization.

Finding counts: 0 blockers, 7 high-risk findings, 17 medium findings, 8 low findings.

## Blockers

None found.

No reviewed issue requires replacing the core architecture. The design can support A1-A14 if the required corrections are made before the affected milestones and if A1 remains constrained to kernel lifecycle, policy hooks, trace propagation, and non-mutating orchestration scaffolding.

## High-Risk Findings

### HIGH-001: A1 lacks an executable kernel and action lifecycle contract

Athena evidence:

- `docs/athena/05-runtime/README.md:19-30` defines lifecycle phases but not valid transitions.
- `docs/athena/05-runtime/README.md:41-49` requires timeouts, idempotency, retries, and rollback but leaves their contract shape open.
- `docs/athena/contracts/README.md:151-172` defines `ActionStatus` as `pending | running | succeeded | failed | cancelled` without persisted step state, attempts, approval pauses, or resume checkpoints.

Repository evidence:

- `app/backend/middleware/productionHardening.ts:18-40` already creates request IDs and logs request duration.
- `app/backend/middleware/errorHandler.ts:26-33` notes that only a small subset of errors are currently normalized.
- `app/db/requestSession.ts:20-41` scopes database sessions to user, org, role, and session source, which Athena must preserve across kernel execution.

Failure mode:

If A1 implements the kernel from the current documentation, a crash, timeout, approval pause, or partial plan failure can leave Athena unable to determine whether to retry, resume, abort, or report completion. That creates duplicate-action risk once real tools arrive in A2-A6.

Smallest correction:

Add an A1 kernel state-machine contract before implementation. It should define plan and step states, legal transitions, terminal states, persisted checkpoints, attempt counters, pause/resume semantics, normalized error categories, and trace propagation requirements. This can be documented as a contract extension rather than production feature code.

### HIGH-002: Timeout, cancellation, and shutdown behavior is not enforceable by tools

Athena evidence:

- `docs/athena/05-runtime/README.md:44` requires timeouts for every action but does not define how tools receive deadlines or cancellation.
- `docs/athena/06-tool-registry/README.md:16-29` defines `execute(input, context)` but no execution context with an abort signal, deadline, request ID, or finalization hook.
- `docs/athena/13-deployment/README.md:44-46` discusses disabling providers/tools during incidents but not in-flight cancellation behavior.

Repository evidence:

- `app/backend/server.ts:75-76` mounts authenticated API routes behind `requireAuth` and `databaseSession`.
- `app/db/requestSession.ts:44-87` shows background work can run inside scoped database sessions, meaning async Athena execution must carry cancellation and trace context outside the original HTTP request.

Failure mode:

A tool can time out from Athena's perspective while still running in the application service layer. The user may see a failure or cancellation while the mutation later succeeds, producing inconsistent audit trails, duplicate retries, and user-visible surprise.

Smallest correction:

Define an `AthenaExecutionContext` or equivalent in the Bible before A1. It should include `requestId`, `executionId`, `traceId`, `deadline`, cancellation signal, actor, organization, approval state, and finalization behavior. Mutating tools must check cancellation before mutation and before returning success.

### HIGH-003: Context contracts can overexpose PII and encourage load-everything behavior

Athena evidence:

- `docs/athena/07-context-engine/README.md:14-33` lists many required context sections, including customers, calendar, dispatch, costbook, inventory, notifications, and telemetry.
- `docs/athena/contracts/README.md:52-82` defines C001 AI Context but does not require per-section sensitivity, redaction policy, max size, field allowlists, or selected scope.
- `docs/athena/contracts/README.md:277-295` defines C010 Context Provider without activation rules, lazy/eager behavior, intent gating, or output limits.

Repository evidence:

- `app/modules/intelligence/types.ts:26-33` allows search documents to carry subtitles, keywords, and metadata.
- `app/modules/intelligence/service.ts:128-157` indexes customer email, phone, and address into global search fields.
- `app/modules/intelligence/service.ts:294-308` fans out global search across all sources when no entity types are provided.

Failure mode:

A naive A1-A3 implementation could assemble broad customer, dispatch, calendar, and notification context for routine prompts. That increases latency, token cost, stale-context risk, and cross-feature data exposure. It also creates a plausible path for PII to reach model prompts, telemetry, memory, or future plugins without an explicit need-to-know decision.

Smallest correction:

Revise C001/C010 before A3, and constrain A1 to minimal request context. Each context section should declare sensitivity, required permission, selected scope, max items, max bytes or estimated tokens, freshness, source references, redaction policy, and whether it was omitted or degraded. High-PII providers should be lazy and intent-gated by default.

### HIGH-004: Context freshness is not auditable enough for consequential actions

Athena evidence:

- `docs/athena/07-context-engine/README.md:43-48` defines freshness labels but not fetched-at, expires-at, cache-hit, source-version, or revalidation proof.
- `docs/athena/07-context-engine/README.md:50-52` says tools revalidate critical data before mutation, but the contract does not specify the evidence retained.
- `docs/athena/contracts/README.md:74-82` only requires context section status when a provider contributes data.

Repository evidence:

- `app/modules/knowledge-runtime/cache.ts:3-12` uses process-level cached source data with no TTL or version surfaced in the contract.
- `app/modules/knowledge-runtime/README.md:50-55` documents deterministic, file-based, in-memory knowledge loading.

Failure mode:

Athena may approve or execute actions based on stale estimates, availability, inventory, schedule, or customer state. Later audit reconstruction would not be able to prove which context snapshot was used, whether it was fresh, or whether a tool revalidated it before mutation.

Smallest correction:

Require freshness metadata for all provider outputs: `fetchedAt`, `expiresAt`, `ttlMs`, `cacheHit`, `sourceVersion` or content hash, `revalidatedAt`, and `freshnessStatus`. Consequential actions should persist the provider evidence used at approval time and the revalidation evidence used at execution time.

### HIGH-005: Object-level permission and field-level context filtering are under-specified

Athena evidence:

- `docs/athena/09-security/README.md:15-23` requires tenant boundaries and capability checks but does not define object-level or field-level filtering.
- `docs/athena/contracts/README.md:206-215` defines C007 Permission as a coarse capability decision.
- `docs/athena/contracts/README.md:277-295` allows providers to declare required permissions but not object scope, assignment scope, or denied fields.

Repository evidence:

- `docs/RBAC_MATRIX.md:16-28` defines canonical roles.
- `docs/RBAC_MATRIX.md:66-75` limits technicians to assigned job and project context.
- `app/backend/requestContext.ts:27-33` checks role-derived permissions, while object-level restrictions must be enforced by services or query scopes.
- `app/modules/intelligence/types.ts:47-50` defines search sources with `orgId` and query but no actor or object-scope parameter.

Failure mode:

Athena could correctly verify that a field technician has a broad capability while still exposing unrelated customer, estimate, invoice, or schedule context inside the same organization. RLS prevents cross-organization leakage, but it does not automatically enforce assigned-job-only visibility.

Smallest correction:

Extend Athena permission and context-provider contracts with resource scope, actor role, assignment scope, denied fields, and service-owned object filtering. Providers should not infer access from role permissions alone; they must ask application services for actor-scoped data.

### HIGH-006: Production-readiness gates are not executable yet

Athena evidence:

- `docs/athena/12-testing/README.md:15-32` names AI evaluation, production smoke tests, performance/load tests, and other Athena-specific layers.
- `docs/athena/13-deployment/README.md:67-74` requires production readiness gates.
- `docs/athena/roadmap.md:15-29` sequences A1-A6 before A10 observability maturity.

Repository evidence:

- `package.json:5-8` currently exposes docs checks only at the root.
- `app/package.json:7-14` exposes backend lint, build, unit, and integration checks.
- `web/package.json:5-11` exposes frontend lint, build, and tests.
- `.github/workflows/verify-repository.yml:16-94` verifies app and web checks, but no Athena-specific contracts, smoke, eval, or performance gates exist yet.

Failure mode:

A1-A6 can be implemented and appear CI-green without proving Athena contract compatibility, lifecycle behavior, tenant-isolation fixtures, model outage handling, cost ceilings, or no-op smoke readiness.

Smallest correction:

Before A1 exits, define the future command names and minimum expected coverage for `athena:contracts`, `athena:smoke`, `athena:eval`, and `athena:perf` or mark those checks as explicit pre-production blockers until implemented.

### HIGH-007: Minimal observability is sequenced too late for tool and action execution

Athena evidence:

- `docs/athena/roadmap.md:16-25` places AI kernel, tool registry, planner, and action engine before A10 observability.
- `docs/athena/13-deployment/README.md:38-40` requires correlation across conversation, request, context, planner, tool, action, model, and cost.
- `docs/athena/contracts/README.md:301-319` defines telemetry, but roadmap sequencing can defer it until after meaningful action execution exists.

Repository evidence:

- `app/backend/logging.ts:1-20` provides generic structured logging.
- `app/backend/middleware/productionHardening.ts:27-40` logs request completion with request ID and duration.
- Current logs do not yet include Athena execution IDs, plan IDs, tool calls, approval IDs, model usage, or cost attribution.

Failure mode:

Early tool/action bugs, duplicate execution, high model spend, stale approvals, or cross-tenant context anomalies may not be reconstructable when they occur. Waiting until A10 to add minimal trace/cost records makes A2-A6 less safe.

Smallest correction:

Move minimal C011 trace, redaction, cost, plan, tool-call, action, and approval records into A1/A2. Leave dashboards, exporters, alerting maturity, and long-term observability polish for A10.

## Medium Findings

### MEDIUM-001: Generic rollback language is too broad

`docs/athena/05-runtime/README.md:64-72` describes rollback modes, but many TradeOS operations cannot be rolled back safely. Sent communications, invoice generation, customer approval, inventory reservations, and schedule notifications require compensating actions rather than reversal.

Correction: Replace generic rollback expectations with a `rollbackPolicy` or `compensationPolicy` per tool/action: `none`, `safeDeleteDraft`, `serviceUndo`, `compensatingAction`, or `manualRepair`.

### MEDIUM-002: Idempotency is named but not anchored to semantic targets

The Bible requires idempotency keys, but it does not distinguish request IDs, action IDs, and semantic business keys. Existing estimating flows already use review tokens/source keys to avoid duplicate AI-assisted writes, as documented in `docs/modules/ai-estimate-assist.md:49-55`.

Correction: Require mutating tools to define a target-specific idempotency strategy, such as `estimateId + sourceKey`, `invoiceId + operation`, or `jobId + scheduleWindow`.

### MEDIUM-003: Event architecture risks overuse for synchronous domain decisions

`docs/athena/10-events/README.md:10-12` says important business changes should emit events. That is correct, but it can be misread as event-first orchestration. Application services should still make synchronous domain decisions and write state transactionally. Events should publish facts after commits.

Correction: Add a decision table for synchronous service calls versus asynchronous event reactions.

### MEDIUM-004: Memory retention controls are prose-first, contract-second

`docs/athena/08-memory/README.md:38-43` requires retention, deletion, and correction, while `docs/athena/contracts/README.md:178-199` does not make actor, audit, visibility, retention policy, correction state, or deletion state required.

Correction: Promote these fields into C006 before any persistent memory implementation.

### MEDIUM-005: Plugin architecture is intentionally future-facing but still too tempting to implement early

`docs/athena/11-plugin-sdk/README.md:10-11` says the plugin SDK is future architecture, but A13 detail may pull effort into sandboxing, marketplace, and third-party lifecycle before first-party tools prove the internal contract.

Correction: Mark plugin runtime, marketplace, third-party secrets, and external distribution as deferred until after first-party tool contracts survive production use.

### MEDIUM-006: Error taxonomy is not specific enough for automated retry decisions

The standard tool result envelope distinguishes failure from success, but it does not define normalized error codes, retryability, safe user summaries, or source categories.

Correction: Add `error.code`, `error.retryable`, `error.category`, `error.safeSummary`, and `error.correlationId` to failure envelopes before A6.

### MEDIUM-007: Planner ambiguity and user correction behavior needs sharper state

The planner contract allows plans and rationale, but ambiguous requests, partial plans, cancellation, and user correction loops are underspecified.

Correction: Add plan states for `needs_clarification`, `awaiting_approval`, `cancelled_by_user`, `replanned`, and `superseded`.

### MEDIUM-008: Observability lacks a precise privacy boundary

Athena correctly avoids chain-of-thought logging, but it does not yet define which tool inputs, outputs, context summaries, memory updates, and model prompts may be logged, redacted, hashed, sampled, or suppressed.

Correction: Add telemetry redaction and sampling policy before A10, and require sensitive payload exclusion by default.

### MEDIUM-009: Background execution and queue replay need tenant-scoped invariants

`app/db/requestSession.ts:44-87` provides a good pattern for scoped background work. Athena should adopt it explicitly for delayed approvals, retries, replay, and event subscribers.

Correction: Require every queued Athena execution, event replay, and scheduled follow-up to carry `orgId`, actor or service principal, role/capability context, request/session source, and trace IDs.

### MEDIUM-010: Context provider cache keys are not explicitly tenant-qualified

`docs/athena/07-context-engine/README.md:37-39` says providers declare caching and freshness behavior, and `docs/athena/contracts/README.md:277-295` makes cache key metadata optional. Sensitive tenant data cannot safely use fallback cache unless the key includes organization, actor or service principal, permission snapshot, provider version, and scoped input.

Correction: Make cache-key requirements mandatory for cached tenant data and add two-organization cache-isolation tests.

### MEDIUM-011: Event replay and dead-letter handling must re-enter scoped database sessions

`docs/athena/10-events/README.md:53-60` defines replay and dead-letter behavior, but the Athena event contract does not explicitly require re-entry through the existing scoped background-session pattern. The repository already provides that precedent in `app/db/requestSession.ts:44-87`.

Correction: Require every Athena subscriber, replay worker, and dead-letter reprocessor to use a service-owned scoped session and validate referenced entity ownership before side effects.

### MEDIUM-012: RBAC ownership is contradictory for Athena service calls

The Bible says application services enforce permissions, but current TradeOS controllers often enforce route permissions before calling services. For example, `app/backend/requestContext.ts:27-33` performs role-permission checks, while services such as `EstimateEngineService.addLineItem` are designed around explicit `orgId` service calls rather than HTTP request objects.

Correction: Document an Athena permission adapter as the deterministic gate before service calls, and require Athena-exposed services to either accept actor/policy context or be wrapped by a policy-checked application service facade.

### MEDIUM-013: Memory persistence needs an application-service boundary

`docs/athena/README.md:53-59` establishes the core dependency rule, but `docs/athena/04-system-architecture/README.md:33-50` and `docs/athena/05-runtime/README.md:19-30` can be read as `Action Engine -> Memory` direct persistence. Because memory is durable, tenant-scoped, auditable state, it should not become a parallel infrastructure path.

Correction: Define `AthenaMemoryService` as the service boundary for memory reads/writes and update diagrams during the next Bible correction pass.

### MEDIUM-014: Some project workspace flows lack Athena-ready service seams

Athena contributor guidance requires tools to call application services, but some project workspace behavior remains controller/direct-Prisma centered in the current backend. Future Athena tools for site visits, project files, or project workspace actions would otherwise need to call HTTP controllers or duplicate business logic.

Correction: Mark those Athena tools blocked until `ProjectWorkspaceService`, `SiteVisitService`, and `ProjectFileService` seams exist or until existing services are identified and documented.

### MEDIUM-015: A3 context scope is broader than current product reality

The required context sections include weather, calendar, dispatch, customers, costbook, Knowledge Engine, inventory, notifications, and telemetry. Current repository truth still identifies some production integrations and supplier ingestion as incomplete or partially verified.

Correction: Split A3 into existing app-backed providers first, then defer external weather, calendar, inventory, and other integration-backed providers behind readiness records.

### MEDIUM-016: Athena must not wrap the weaker legacy AI estimate apply path

The Bible correctly says AI Estimate Assist remains review-first, and `docs/modules/ai-estimate-assist.md:49-55` documents stronger review-token/source-key behavior. Current legacy AI estimate apply routing still exists and should not become the easiest Athena integration path.

Correction: Explicitly forbid Athena tools from using legacy AI apply routes that lack the structured review-token/idempotency safeguards, or harden/deprecate those routes before exposure.

### MEDIUM-017: Performance and cost budgets are not concrete enough to stop amplification

`docs/athena/13-deployment/README.md:56-63` names latency, cost, and fallback SLIs without numeric budgets. Existing Knowledge Runtime search and structured estimating are deterministic but can become expensive when multiplied by context-provider fanout, planner retries, and model calls.

Correction: Define initial A1/A3/A5 guardrails for maximum providers, maximum tool calls, maximum context bytes or tokens, maximum retries, cache TTL behavior, and cost attribution.

## Low Findings

### LOW-001: Contract fields should be tiered into v1 required, v1 optional, and deferred

The contract catalog is thorough, but several future fields may slow A1 if treated as implementation requirements immediately.

Recommended v1 required:

- `executionId`, `requestId`, `orgId`, `actor`, `traceId`, `toolName`, `toolVersion`, `risk`, `requiredPermissions`, `inputSchema`, `resultEnvelopeVersion`, `idempotencyKey` for mutating tools, `deadline`, and `auditPolicy`.

Recommended v1 optional:

- `costEstimate`, `modelHints`, `compensationPolicy`, `providerFallbacks`, `humanReviewTags`, and `semanticVersionRange`.

Recommended deferred:

- marketplace metadata, third-party commercial terms, public plugin distribution, provider marketplace compatibility, and generalized multi-agent marketplace controls.

### LOW-002: Roadmap should explicitly freeze A1 scope

`docs/athena/roadmap.md:15-29` lists A1 as AI kernel. Add an A1 note that no production business tool may mutate records until A2 registry, A4 permissions, and A6 action engine gates exist.

### LOW-003: ADR revisit dates would improve governance

The ADRs include revisit conditions, but no target milestone or owner. Adding a milestone-based review tag would make drift easier to catch.

### LOW-004: Naming should reserve "Knowledge Engine" versus "Knowledge Runtime"

The Bible mentions Knowledge Engine while the repository has `app/modules/knowledge-runtime`. Add a glossary mapping so future implementers do not create a parallel subsystem accidentally.

### LOW-005: Tool-result event ownership is ambiguous

Tool results include `events`, while event rules say application services publish canonical events and tools do not unless explicitly delegated.

Correction: Clarify that tool-result events are references to service-published events unless a tool has explicit delegated publisher authority.

### LOW-006: Pricing formula ownership should be clarified before costbook tools

Current costbook and assembly modules import pricing helpers from `estimate-engine`, while `EstimateEngineService` imports costbook services. That does not block A1, but it could confuse future costbook/estimating tool boundaries.

Correction: Document the current dependency as accepted for now or later move shared pricing formulas to a neutral domain utility.

### LOW-007: Generic intelligence entity references are not ownership proofs

Activity, notification, recent-item, and related intelligence rows can reference entity type and ID within an org. Future Athena context or memory code should not treat those references as proof the target entity exists or belongs to the same org.

Correction: Add an entity-ownership resolver before Athena dereferences generic intelligence references.

### LOW-008: Athena docs are not yet wired into docs governance

The Athena Bible declares itself source-of-truth architecture documentation, but docs index and ownership rules do not yet mechanically recognize `docs/athena/**`.

Correction: Add `docs/athena/**` to the docs index and ownership map in a later governance PR or a narrow follow-up to the Bible PR.

## Architecture Strengths

- Athena's dependency direction matches TradeOS architecture: `Athena -> Tool -> Application Service -> Domain Logic -> Infrastructure`.
- The Bible correctly treats the LLM as non-authoritative for authorization and business state.
- Current TradeOS request scoping through auth, organization membership, and forced database sessions provides a strong foundation for Athena execution.
- Existing AI Estimate Assist and Knowledge Runtime already model the right posture: advisory AI, deterministic retrieval, human review, and writes through application services.
- The Platform Bible is versionable and reviewable; contracts and ADRs are separated cleanly.

## Contract Gaps

- C001 AI Context needs section sensitivity, selected scope, size limits, freshness evidence, and omission/degradation metadata.
- C002 Tool needs an execution context separate from AI context.
- C003 Tool Result needs normalized error details and retryability.
- C004 Planner needs explicit plan states, replanning, clarification, supersession, and approval-pause behavior.
- C005 Action needs lifecycle transitions, attempts, checkpoints, cancellation, and compensation policy.
- C006 Memory needs actor, audit, retention, visibility, deletion, correction, and trust state as first-class fields.
- C007 Permission needs resource/object scope and denied-field output, not only capability decisions.
- C008 Event needs clearer sync-versus-async guidance and replay authorization invariants.
- C010 Context Provider needs activation mode, intent gating, scope inputs, and output budgets.
- C011 Telemetry needs redaction, sampling, retention, and payload classification rules.
- C012 Plugin should clearly mark marketplace and third-party runtime features deferred until A13.
- Production validation contracts need named commands or explicit pre-production gate language.

## Security Findings

- The Bible is correct that authorization must be outside the LLM, but the permission contract must model object-level access before field-technician or office-manager workflows are automated.
- Prompt injection controls are directionally correct, but untrusted external content should be tainted through context, memory, planner, and tool execution artifacts.
- Secrets handling for plugins is future-facing; it should remain deferred until the first-party internal tool registry is stable.
- Approval gates must persist approval actor, timestamp, approved action payload hash, and expiration so a modified plan cannot reuse stale approval.
- Athena-exposed service calls need deterministic policy enforcement because current controller-level RBAC is not always inside service methods.

## Multi-Tenant Findings

- No direct cross-tenant bypass was found in the Bible's stated architecture.
- The highest plausible leakage path is broad org-scoped context assembly combined with coarse permission checks and future plugin/tool access.
- Tenant-scoped memory, telemetry, cached context, queued actions, event replay, and background retries must all carry `orgId` and actor/service-principal context.
- RLS is necessary but not sufficient for Athena context visibility because assigned-resource restrictions are finer grained than organization boundaries.
- Event replay and dead-letter processors must re-enter scoped background database sessions instead of trusting event payloads directly.

## Performance/Cost Findings

- The largest expected bottleneck is context construction, especially if the required context sections are interpreted eagerly.
- Global tool discovery should be registry-filtered before model planning, not exposed as a large prompt catalog every turn.
- Memory retrieval should use bounded top-K and source references, not full memory hydration.
- Event publishing and audit logging should be batched or outboxed where possible, but audit-critical writes must not be silently dropped.
- Recommended A1 targets should be treated as engineering budgets, not claims: one kernel execution record per request, minimal context assembly, bounded tool catalog, no external business tool fanout, and deterministic failure behavior before model optimization work.
- Observability must start in A1 as minimal execution tracing and cost attribution; A10 should mature observability rather than introduce it.

## Over-Engineering Risks

- Third-party plugin marketplace design can wait until first-party tools validate the tool contract.
- Multi-provider abstraction should be limited to a small provider adapter boundary until a second provider is actively needed.
- Generic rollback should not become a platform-wide abstraction. Most business actions need explicit compensating-action policy.
- "Everything important emits events" should not replace direct transactional application-service writes.
- Subagents should not be exposed as public product concepts or independent mutating actors in early milestones.

## Under-Specified Areas

- Kernel state machine, persistence, and lifecycle transitions.
- Execution context separate from AI context.
- Cancellation, shutdown, and timeout propagation.
- Minimal Athena-specific validation command names and gate ownership.
- Approval expiration and payload binding.
- Context minimization, redaction, and selected resource scope.
- Memory admin inspection and correction UI/API boundaries.
- Event outbox, replay authorization, and dead-letter ownership.
- Tool result error taxonomy.
- Telemetry payload redaction and retention.
- Test fixtures for tenant isolation across context, memory, events, and queued work.

## Recommended Bible Corrections

These are documentation corrections recommended before or during A1. They are not production code changes.

1. Add an A1 kernel lifecycle contract covering states, transitions, attempts, checkpointing, cancellation, timeout, shutdown, and trace propagation.
2. Add an execution-context contract used by tools, distinct from AI context.
3. Tighten C001 and C010 to require context minimization, sensitivity classification, selected scope, max size, freshness evidence, and provider activation mode.
4. Extend C007 to include resource scope, denied fields, and object-level service authorization.
5. Add payload-hash and expiration requirements to approval records.
6. Replace generic rollback language with explicit compensation-policy language.
7. Add sync-versus-async event guidance so services remain the owner of transactional business decisions.
8. Mark third-party plugin runtime, marketplace, external secrets, and public distribution as deferred until after first-party tools prove the registry.
9. Add Athena-specific validation command names or explicitly state when each gate becomes mandatory.
10. Add a rule that Athena tools may not call legacy AI apply paths that lack review-token and idempotency safeguards.

## Deferred Decisions

- Which model provider or providers Athena will use in production.
- Whether Athena needs multi-agent execution beyond invisible internal orchestration.
- The plugin marketplace business model and external developer review process.
- Voice/mobile-specific streaming UX.
- Long-term storage backend for memory.
- Exact performance budgets for model latency and context assembly after the first A1 prototype is measured.

## A1 Readiness Checklist

A1 may begin when these are true:

- The A1 implementation scope is limited to a non-mutating kernel foundation.
- The kernel has persisted execution IDs, trace IDs, plan/step state, attempts, and terminal outcomes.
- The kernel has a normalized error taxonomy and safe user-facing failure summaries.
- The kernel passes actor, org, role, capability, and request/session source through execution.
- The kernel emits minimal trace and cost metadata from the first executable milestone.
- Tools receive deadlines and cancellation signals before any mutating tool is implemented.
- Context assembly in A1 uses minimal request context only; broad business context waits for A3 contract corrections.
- No LLM output can authorize, approve, or directly mutate state.
- No production database access occurs outside existing application services and scoped database sessions.
- A1 includes deterministic tests for lifecycle transitions, cancellation, timeout, permission denial, and audit record creation.

## Recommended A1 Scope

A1 should build the smallest useful AI kernel:

- Kernel entrypoint that accepts authenticated request metadata and conversation input.
- Execution record creation with `executionId`, `requestId`, `orgId`, actor, trace ID, lifecycle state, and timestamps.
- Minimal AI context containing request, organization, authenticated user, permissions summary, conversation reference, and telemetry metadata.
- Provider adapter seam for one model provider, without broad multi-provider orchestration.
- Planner stub or no-op planner that can produce non-mutating draft responses.
- Tool execution disabled or limited to safe documentation/demo fixtures until A2 registry and A4 permissions land.
- Normalized error handling, timeout handling, cancellation handling, and audit-safe summaries.

## Recommended A2+ Sequencing

1. A2 Tool Registry: Implement internal first-party registry with strict metadata, result envelope, versioning, and no third-party runtime.
2. A3 Context Engine: Add lazy, scoped, sensitivity-aware providers with freshness evidence and size budgets.
3. A4 Permissions: Bind Athena permissions to existing roles, organization membership, RLS session behavior, and object-level service checks.
4. A5 Router/Planner: Add deterministic routing guardrails before model-driven planning.
5. A6 Action Engine: Add approval gates, idempotency, sequential/parallel step execution, and compensating-action policy.
6. A7 Memory: Implement only after admin inspection, correction, deletion, retention, and poisoning controls are ready.
7. A8 Event Integration: Publish facts after committed service writes; use outbox/dead-letter/replay controls.
8. A9 Tool SDK: Formalize first-party tool developer workflow after several internal tools exist.
9. A10-A14: Add observability hardening, security drills, business tool rollout, plugin SDK, and voice/mobile readiness in that order.

## Final Go/No-Go Recommendation

Go for A1 only with required corrections.

A1 should begin as a constrained kernel-readiness milestone, not a product-feature milestone. Do not implement autonomous business actions, broad context hydration, persistent long-term memory, or third-party plugins in A1.

If the A1 team accepts the lifecycle, execution-context, context-minimization, and permission-scope corrections above, the Athena architecture is ready to move forward without foundational redesign.
