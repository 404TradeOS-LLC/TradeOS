# A12.1 — Transactional Event Reliability

## Status

Implementation follow-up to A12. This work must land before A13 begins.

Tracking issue: #144.

## Problem

A12 added canonical Athena business-event publication for estimate and job mutations by following the existing `ProposalsService.send()` pattern. Several service methods currently perform the business mutation and then call `AthenaEventService.publish()` with a catch-and-log fallback.

That pattern is not a strong service-level guarantee: if durable event persistence fails after the business mutation has committed, business state can exist without the canonical Athena event that should describe it.

Request-scoped HTTP execution often already supplies an outer database transaction through `runWithDatabaseSession()`, but application services must not rely on a controller/request wrapper to preserve their domain invariant. The service boundary itself must guarantee mutation/event atomicity.

## Architecture Decision

Do **not** add a second outbox table.

`athena_events` and `athena_event_deliveries` already are the durable transactional outbox:

- `AthenaEventRepository.createEventWithDeliveries()` writes the event and subscriber delivery fan-out atomically.
- `runInDatabaseTransaction()` reuses an active request transaction through `AsyncLocalStorage`, or opens a transaction when no request transaction exists.
- the Prisma proxy routes event-repository writes to that active transaction.

The repair is therefore to widen the **application-service transaction boundary** so the business mutation and `publish()` call share the same transaction.

## Required Publishers

This follow-up covers all current production canonical publishers so the invariant is consistent:

1. `EstimateEngineService.create()` → `EstimateStarted`
2. `EstimateEngineService.finalize()` → `EstimateCompleted`
3. `JobsService.schedule()` → `JobScheduled`
4. `JobsService.addAssignment()` → `TechnicianAssigned`
5. `JobsService.complete()` → `WorkCompleted`
6. `ProposalsService.send()` → `ProposalSent`

No additional event types are introduced.

## Transaction Semantics

For each covered mutation:

1. open or reuse `runInDatabaseTransaction(...)`;
2. validate and perform the business mutation;
3. persist the canonical Athena event through `AthenaEventService.publish()` before leaving that transaction;
4. return the actual persisted event reference when the public response already exposes one;
5. commit only after both business state and event persistence succeed.

If event persistence fails, the transaction fails and the business mutation rolls back. The service must not swallow that persistence failure.

This does **not** change subscriber semantics. Subscriber execution remains asynchronous/pull-based. A subscriber failure, retry, or dead-letter happens after the business transaction has committed and must never roll back that committed business state.

## Idempotency

Preserve all existing idempotency keys and event versions. This follow-up must not create a second canonical event for a repeated idempotent operation.

## Compatibility

- Preserve existing DTO fields and existing optional `athenaEvent` response shape where already exposed.
- Do not add new REST routes.
- Do not add a scheduler or production subscriber.
- Do not change A4 permissions, A9 Tool SDK contracts, A10 telemetry, or A11 security behavior.
- Do not begin A13 work.

## Verification

Required evidence before merge:

- focused tests proving event-persistence failure rolls back each covered business mutation or representative shared seam;
- existing estimate/job/proposal service tests remain green;
- Athena event unit, contract, and integration tests remain green;
- app lint/typecheck and build pass;
- repository docs checks pass.

## Deferred Scheduler-Readiness Risk

`AthenaEventRepository.findDuePendingDeliveries()` currently uses an ordinary due-row query and does not claim rows with `FOR UPDATE SKIP LOCKED` (or an equivalent lease/claim mechanism). That is acceptable while production has no concurrent dispatch scheduler. Before more than one dispatch worker can run for an organization, add explicit row claiming so two workers cannot dispatch the same due delivery concurrently.

That concurrency hardening is deliberately separate from this transaction-boundary repair.
