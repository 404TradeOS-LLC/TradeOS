# Resend transactional email and delivery callback

## Current sending path

TradeOS uses the server-only `EmailService` in `app/modules/email/service.ts` for password-reset links, team invitations, and one-time customer-portal access links. The sender is `TradeOS <hello@404tradeos.com>` through Resend's verified `404tradeos.com` domain. Google Workspace remains responsible for incoming mailbox delivery and its DNS records must not be replaced with Resend inbound MX records.

The provider uses `RESEND_API_KEY`, `EMAIL_FROM`, and an HTTPS `APP_BASE_URL`. Token links are generated by the server with opaque identifiers, and provider errors must never reveal those values. The application currently renders branded HTML and plain-text email directly in the service. The published Resend dashboard templates (password reset, team invitation, customer portal access) are reusable assets but **are not automatically invoked** by this service. Changing to template-id sending requires separate behavior tests and protected acceptance.

## Signed delivery callback (draft pilot)

The `POST /api/v1/webhooks/resend` route is mounted **before** `express.json()` and user-authenticated middleware, using a 64-KiB raw JSON body limit. It checks `svix-id`, `svix-timestamp`, and `svix-signature` with an HMAC-SHA256 signature over the exact raw bytes, a five-minute timestamp tolerance, and constant-time comparison. Requests are IP-rate-limited to 120 per minute on each runtime instance; this is a bounded abuse defense, not a distributed edge-wide quota. Every request is denied if `RESEND_WEBHOOK_SECRET` is absent or malformed. The secret is an independent server-only value, not the Resend sending API key.

The pilot only writes minimal verified event-type metadata to the structured server log and returns HTTP 200. It does **not** persist email delivery status, perform suppression, update tenant/customer records, or deduplicate repeated valid events across instances. The endpoint's lack of tenant writes avoids cross-tenant side effects; it does **not** establish end-to-end exactly-once processing.

**Do not register an active production Resend webhook against this endpoint yet.** If connected now, a bounced or complained event would be acknowledged without durable suppression, and retries could not recover that loss.

## Staged acceptance and release

1. Confirm the exact GitHub head SHA, required CI, review threads, and branch currency.
2. Obtain explicit authorization for a protected staging-only deployment and provision a dedicated `RESEND_WEBHOOK_SECRET`; never disclose its value or put it in `NEXT_PUBLIC_*`.
3. Check unsigned, tampered, stale, malformed, and correctly signed webhook requests at the matching immutable staging API URL; retain signed-response evidence without storing secrets or recipient PII.
4. Before registering real delivery callbacks, design and test a durable idempotent event journal keyed by provider webhook ID, transactionally map outbound message IDs to their originating tenant, and suppress hard-bounced/complained recipients without cross-tenant writes.
5. Register the webhook only after its delivery handlers and tenant isolation pass staging, then verify Resend's live test callback and independent release approval. Production environment secrets and deployment promotion remain separately protected.

## Verification boundaries

Resend's `delivered` status confirms acceptance by the recipient mail server; it does not prove an email was opened. A direct Resend-to-mailbox smoke test also does not prove the currently deployed TradeOS API has the necessary environment bindings, and Vercel environment metadata must be verified independently before claiming application-level send readiness.
